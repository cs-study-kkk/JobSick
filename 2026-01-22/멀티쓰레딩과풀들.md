# 동시성 문제의 핵심 3대장
- Race Condition (경쟁 상태)
- Deadlock (교착 상태)
- Context Switching 비용

---

## 1. Race Condition (경쟁 상태)

### 1.1 정의
Race Condition이란  
**여러 스레드가 공유 자원(shared resource)에 동시에 접근하고,  
실행 순서에 따라 결과가 달라지는 상태**를 말한다.

핵심 포인트:
- "동시에 실행"이 아니어도 "동시에 접근 가능"하면 발생
- DB에서 Dirty Read / Non-repeatable Read / Phantom Read랑 비슷 문제, 다만 발생하는 수준이 메모리 수준 / DB 수준인지의 차이
---

### 1.2 왜 발생하는가?
CPU 연산은 원자적(atomic)이지 않다.

다음 연산은 한 줄이지만 실제로는 여러 단계로 나뉜다.
```text
count = count + 1
↓
1) count 읽기
2) +1 연산
3) count 쓰기
```

이 사이에 다른 스레드가 끼어들면 문제가 발생한다.

---

### 1.3 예시 (Java 스타일 의사 코드)

```java
class Counter {
    int count = 0;

    void increment() {
        count++; // atomic하지 않음
    }
}
```

```java
Thread A: count = 0 읽음
Thread B: count = 0 읽음
Thread A: count = 1 저장
Thread B: count = 1 저장
```

기대값: 2  
실제값: 1 ❌

---

### 1.4 특징
- 재현이 어렵다
- 로그를 찍으면 사라진다
- 운영 환경에서만 터진다


#### 재현이 어려운 이유

위와 같은 문제가 발생하는 이유는 실행 순서가 달라지기 때문이다.
실행 순서는 개발자가 정하는 것이 아니라 CPU 상태, OS, 캐시, 인터럽트 타이밍 등에 의해 결정된다.
따라서 같은 코드를 실행해도 다른 결과가 발생 가능하다.


#### 로그를 찍으면 사라지는 이유

로그는 단순히 로그가 아니라 꽤나 복잡하고 무거운 명령어.
문자열 생성, 분기 예측, LOCK 관련 등 작업이 포함됨

따라서 우연히 어긋난 타이밍이 맞춰질 수 있고, 로그 한줄로 인해 오류가 해결된 것 처럼 보일 수 있다.
하지만 로그를 다시 지운다면?

#### 운영 환경에서 터지는 이유

영향을 주는 요소들이 운영 환경에서 특히 치명적인 부분이 많다.
네트워크 지연, 동시 접근 확률, context switch 빈도, 캐시 불일치 등.
개발 환경보다 운영 환경에서 문제가 생길 가능성이 높은 요소들이다.

---

### 1.5 해결 방법
- Lock (synchronized, mutex)
- Atomic 변수
- 불변 객체(Immutable Object)
- Node.js처럼 단일 스레드 모델 사용

#### lock을 걸게 된다면?

deadlock 가능성 커짐, 성능 저하됨, 범위가 커질수록 병렬성은 줄어들음
하지만 직관적이고, 구현이 쉽다. 상황에 맞는 적절한 락 필요

#### Atomic 변수란?

연산 자체를 원자적(Atomic)으로 보장하는 방법이다.  
중간에 다른 스레드가 끼어들 수 없는 CPU 수준의 연산을 사용한다.

```java
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();
```

내부적으로 CAS(Compare-And-Swap) 사용 (CAS란? : 내가 마지막에 본 값과 지금 값이 같아야만 연산 수행 )
즉 기다림이 없고, 재시도만 존재한다. 따라서 LOCK이 없으니 DEADLOCK도 없다.
스레드가 멈췄다 꺼지지 않는다. ( 단순 명령어 1개이고, 락도 없으니 ) 


CAS 방식인 만큼, 복합적인 변화에는 취약하다. 여러 필드를 동시에 변경하는 경우, 하나라도 불일치 한다면 전체 재시도이기 때문에
동일한 원리로 값이 적더라도 복잡한 작동 로직을 갖는 경우에도 문제가 발생한다

간단한 경우에만 사용 가능

#### 불변 객체와 단일 스레드 모델

불변 객체의 경우 READ만 허용, READ끼린 충돌이 나지 않는다.

단일 스레드의 경우 동시 접근이 불가능하다.

동시성 문제 자체를 회피

## 2. Deadlock (교착 상태)

### 2.1 정의
Deadlock이란  
**두 개 이상의 스레드가 서로가 가진 자원을 기다리며  
영원히 멈춰 있는 상태**를 말한다.

---

### 2.2 Deadlock 발생 4조건 (중요)

Deadlock은 아래 4가지가 **모두 만족**될 때 발생한다.

1. Mutual Exclusion (상호 배제)
2. Hold and Wait (보유하며 대기)
3. No Preemption (강제 회수 불가)
4. Circular Wait (순환 대기)

---

### 2.3 예시

```java
Object lockA = new Object();
Object lockB = new Object();

Thread 1:
synchronized(lockA) {
    synchronized(lockB) {
        // 작업
    }
}

Thread 2:
synchronized(lockB) {
    synchronized(lockA) {
        // 작업
    }
}
```

---

### 2.4 실행 흐름

```text
Thread 1: lockA 획득
Thread 2: lockB 획득
Thread 1: lockB 대기
Thread 2: lockA 대기
```

→ 서로 기다리기만 함  
→ **영원히 진행 불가**

---

### 2.5 특징
- CPU 사용률은 낮음
- 시스템은 살아 있지만 요청이 처리되지 않음
- 재시작 전까지 복구 불가

실제 연산을 하고있지 않고 대기중이니 CPU 사용량은 낮음.
프로세스는 살아있다. 하지만 스레드가 교착상태이므로 실제 요청이 들어와도 처리할 수 없다.
요청은 들어가지만 응답은 오지 않는 상태가 된다.
해결법은 프로세스를 종료하는 것. (재시작)

---

### 2.6 해결 방법
- Lock 순서 통일
- Timeout 있는 Lock 사용
- Lock 범위 최소화
- 가능하면 Lock 자체를 제거 (불변 구조, 메시지 기반)

Lock 순서 통일은 구조적으로 A,B,C가 있을 때 LOCK 획득 순서를 A,B,C 로 정하자는 것이다.
하지만 현실적으로 매우 어렵다. ( 다른 파트와도 통일, 신규 개발자 투입에 어려움, 실수하기 쉬움 )

Timeout이 있는 LOCK을 이용하는 법은 Deadlock을 완전히 피하는 것이 아니라 영원히 멈춰있는 상태를 피하는 것.
synchronized(lock)의 경우 영원히 대기하지만, ReentrantLock는 대기 시간동안만 대기한다.
자연스레 시간제한을 어떻게 잡아야 할지 문제와, 잘못 잡은 경우 멀쩡한 요청도 실패할 수 있다.
또한 시간이 항상 정확하게 일치하는 것이 아니기 때문에 개발환경에선 되지만 운영환경에서 안되거나, 확률적 실패 문제도 존재할 수 있다.

LOCK 범위 최소화는 말 그대로 범위를 필요한 부분에만 적용하는 것이다.
하지만 근본적인 해결책은 아니고, 문제가 발생할 확률을 줄이는 것에 가깝다.

LOCK을 쓰지 않는다면 DEADLOCK도 없다.
이를 이용하는 방법이 불변 구조와 메시징 시스템이다.

메시지 기반 설계는 멀티스레드를 상태 변경에 이용하지 않는 것이다.
전통적인 방식에서 요청 A,B,C 가 공유 자원을 변경하는 각각의 스레드를 생성하였을 때 문제가 발생할 수 있다.

메시징 방법에서는 요청 A,B,C가 들어오면 PRODUCER이 MQ에 전달한다. 예를 들어 A는 a,b를 수정, B는 b를 수정, C는 c를 수정이라면 (a,b,c는 공유 자원)
Producer가 다음과 같은 메시지를 발행한다. (A : a 수정), (A : b 수정 ), (B : b 수정), (C : c 수정) 이렇게
그럼 큐에도 이제 나뉘어서 들어간다. (a 스트림 : (A:a] b 스트림 : (A:b],(B:b],,) 이렇게
실제 처리하는 CONSUMER은 이제 들어온 요청에 따라 처리를 수행한다. 이미 직렬화 되어있기 때문에
자원별로 메시지 스트림을 분리하고,
각 스트림 내부에서는 직렬 처리로 순서를 보장한다

---

## 5. 핵심 요약 문장

- Race Condition은 "운 좋게 돌아가는 코드"를 만든다
- Deadlock은 "끝나지 않는 기다림"이다


# 2. Thread Pool (스레드 풀)

## 2.1 왜 Thread Pool이 필요한가?

멀티스레딩을 한다고 해서  
요청마다 스레드를 새로 생성하면 문제가 생긴다.

### 스레드 생성 비용
- OS 레벨 자원 할당
- 스택 메모리 할당
- Context 생성  
→ 생각보다 비싸다

### 문제 상황 (요청당 스레드 생성)
- 요청 1,000개 → 스레드 1,000개
- Context Switching 폭증
- 메모리 고갈
- CPU는 일보다 스케줄링에 더 많은 시간 사용

---


## 2.2 Thread Pool이란?

Thread Pool이란  
미리 일정 개수의 스레드를 생성해두고,  
작업(Task)을 큐에 넣어 재사용하는 구조이다.

`
[요청] → [작업 큐] → [Thread Pool] → [실행]
`

핵심:
- 스레드는 생성/삭제가 아니라 재사용
- 작업만 바꿔 끼움

## 2.3 Thread Pool의 구성 요소

1. Worker Thread  
   - 실제 작업을 수행하는 스레드
2. Task Queue  
   - 실행 대기 중인 작업 저장
3. Thread Pool Manager  
   - 스레드 개수 관리  
   - 큐 상태 모니터링

---

## 2.4 Thread Pool의 장점

- 스레드 생성 비용 감소
- 시스템 자원 사용량 예측 가능
- Context Switching 감소
- 서버 안정성 향상

전통적인 서버 구조에서 필수

---

## 2.5 Thread Pool의 단점 & 위험

### 1) Pool 고갈 (Thread Starvation)

- 모든 스레드가 BLOCKING 작업 중
- 새로운 요청이 큐에서 대기만 함

```
Thread Pool (10개)
↓
DB I/O에서 전부 대기
↓
새 요청 처리 불가
```

너무 적어도 너무 많아도 안된다.
20개의 스레드가 있지만 CPU 코어가 8개인 경우, 8개의 작업만 동시에 처리 가능, 나머지 12개는 대기
이때 바꾸는 것이 context swtiching
이게 너무 잦아지면 성능 저하가 발생한다.
너무 많은 스레드를 설정해도, 메모리를 쓰기 때문에 비효율적


---

### 2) 잘못된 크기 설정

- 너무 작음 → 병목
- 너무 큼 → Context Switching 증가

---

## 2.7 Thread Pool과 Deadlock의 관계

Thread Pool이 있다고 Deadlock이 사라지지 않는다.  
오히려 더 위험해질 수도 있다.

### 예시
- Thread Pool: 10개
- 작업 A가 작업 B 결과를 기다림
- 작업 B도 같은 풀을 사용

→ 풀 안에서 서로 기다리며 논리적 Deadlock

김치볶음밥 위에 계란후라이를 올려야 함.
팬은 10개, 팬 10개에 김치볶음밥을 만들고 있음.
계란후라이 만들 팬을 대기하게 된다.

이 문제를 해결하기 위해서는 어떻게 해야할까?

# 3. Connection Pool (커넥션 풀)

## 3.1 DB Connection이 왜 비싼가?

DB Connection 생성 과정:
- TCP 연결
- 인증
- 세션 생성
- 트랜잭션 환경 구성

매 요청마다 생성하면 매우 비효율적

---

## 3.2 Connection Pool이란?

Connection Pool이란  
미리 DB 연결을 여러 개 만들어두고,  
필요할 때 빌려주고 반납받는 구조이다.

```
[요청] → [Connection Pool] → [DB]
              ↑
            반납
```

---

## 3.3 Connection Pool의 기본 동작

1. 서버 시작 시 N개의 Connection 생성
2. 요청 시 하나를 대여
3. 작업 완료 후 반드시 반납
4. 다음 요청이 재사용

---

## 3.4 Connection Pool의 장점

- DB 연결 비용 제거
- 응답 시간 감소
- DB 부하 제어 가능
- 최대 동시 접근 수 제한 가능

DB 보호 장치 역할

---

## 3.5 Connection Pool에서 자주 터지는 문제

### 1) Connection Leak (치명적)

- Connection을 반납하지 않음
- Pool 고갈
- 모든 요청 대기 상태

```
원인:
- 예외 발생 시 close() 누락
- early return
```

---

### 2) Pool 크기 부족

- Thread Pool > Connection Pool
- 스레드는 많은데 DB는 못 감

```
Thread Pool: 50
Connection Pool: 10
→ 40개 스레드 대기
```

---

### 3) Pool 크기 과다

- DB가 처리할 수 있는 커넥션 초과
- DB 성능 급락
- 전체 시스템 느려짐

---

## 3.6 Thread Pool vs Connection Pool 관계 (중요)

핵심:
- Thread Pool ≥ Connection Pool ❌
- Thread Pool ≤ Connection Pool ❌
→ 상황에 따라 다르다

하지만 일반적인 서버에서는:

```
Thread Pool ≥ Connection Pool
```

이유:
- 모든 스레드가 항상 DB를 쓰는 것은 아님
- 일부는 계산, 일부는 캐시, 일부는 I/O

---

## 3.7 실무에서의 전형적인 구조

```
[Client Request]
      ↓
[Thread Pool]
      ↓
[Business Logic]
      ↓
[Connection Pool]
      ↓
[Database]
```

- Thread Pool: 서버 처리량 제어
- Connection Pool: DB 보호

---

결론적으로 pool은 미리 생성해놓고, 연결해서 사용하는 것
