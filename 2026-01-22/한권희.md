# 웹소켓과 SSE

## 왜 실시간 통신 기술이 필요?

기본적으로 우리가 컴퓨터 사이 소통 방식에 대해 주로 알고 있는 방식이 HTTP 기반이다.

HTTTP는 클라이언트가 서버에 메세지를 보내고 서버가 클라이언트에 메세지를 보내는 단방향 형식으로 이뤄진다(HTTP/1.1)

채팅이나 주식 차트처럼 실시간성이 중요한 서비스에서는 서버의 데이터 업데이트를 즉각적으로 클라이언트에게 전달해야 하는데, 기존 HTTP 방식으로는 한계가 있다.

상대방이 메세지를 보냈을 때 이를 감지하는게 안됨

- 이를 polling으로 클라이언트가 주기적으로 서버에 요청을 보내 상대가 새 채팅을 보냈는지 확인하게 할 수 있다.
- 문제
    - 요청을 보내는 주기 만큼 지연 발생 → 즉각적인 반응 아님
    - 요청의 주기가 짧으면 반응이 빠르겠지만 트레픽 낭비가 심해짐
- Long Polling도 있다.
    - 서버가 클라이언트의 요청에 바로 응답하지 않고 데이터(업데이트)가 생길 때까지 기다린다.
    - 상대방이 메시지를 보낼 때(이벤트 발생) 혹은 설정된 타임아웃 시간이 지났을 때 비로소 응답
        - 데이터가 있을 때만 응답하므로 폴링보다 반응 속도는 빨라지지만 서버의 부담 커짐, 여러  클라이언트가 서비스 사용하면 연결을 유지 → 부하 → 업데이트 느려짐
- 따라서 클라이언트와 서버가 동등하게 메세지를 주고 받는 양방향 통신이 가능한 방식이 필요하다

## WebSocket

서버와 클라이언트 간에 **양방향** 통신을 지원하는 기술. 전화 통화처럼 연결된 상태에서 서로 자유롭게 데이터를 주고받을 수 있다.

### **작동 원리 (Handshake)**

1. **요청**: 클라이언트가 HTTP를 통해 "웹소켓 연결 요청"을 보낸다.
    - 헤더에 `Upgrade: websocket`, `Connection: Upgrade`를 포함해 연결을 요청
2. **수락**: 서버가 이를 수락하면 `101 Switching Protocols` 응답을 보내며 프로토콜 전환을 알린다.
3. **연결**: 연결이 수립되면 HTTP가 아닌 WebSocket 프로토콜(`ws://` 또는 `wss://`)로 전환되어 지속적인 연결이 유지된다.

- 한 쪽이 close 프레임을 보낼 때 까지 연결이 이뤄짐

### 연결 관리

- 지정된 시간동안 메세지가 없으면 확인 패킷 보내기
- 주기적 ping/pong 프레임 주고 받으며 연결상태 확인

하는 방법이 있다.

웹 소켓은 하나의 연결을 끝까지 유지하고 그 과정에서 적은 자원만 쓰기에 long polling보다 서버에 부담이 적다.

### 단점

- 서버의 설계에 따라 구현이 복잡하다.

로드 벨런싱을 적용 하면 

(*로드 밸런싱: 하나의 창구에서 서버 여러대가 클라이언트 요청을 나눠 받는거)

 웹소켓은 특정 서버와의 지속적인 연결 안에서 이뤄지기에 한 서버와 웹 소켓 통신을 시작하면 계속 그 서버랑 연결되게 해야하는데 이를 로드벨런싱에서 관리가 복잡하다.

- **로드밸런서의 딜레마**
    
    일반적인 HTTP 요청은 매번 독립적이라 1번 요청을 A서버가, 2번 요청을 B서버가 처리해도 상관없지만 웹소켓은 처음에 **A서버와 핸드쉐이크를 맺었다면, 연결이 끊어질 때까지 계속 A서버하고만 통신해야한다.**
    그런데 로드밸런서는 기본적으로 트래픽을 여러 서버에 골고루 분산시키려고 한다. 
    
    만약 로드밸런서가 웹소켓 메시지를 연결된 A서버가 아닌 B서버로 보내버리면, B서버는 '어? 나랑 연결한 적 없는데?' 하고 연결이 끊기게 된다.
    
    따라서 웹소켓을 쓸 때는 클라이언트가 처음 연결한 서버에 계속 붙어있도록 해주는 **'스티키 세션(Sticky Session)'** 같은 별도의 기술적 처리가 필요하다.
    
- 웹소켓의 기본 프로토콜인 ws는 통신이 암호화 안됨 ⇒ wss
- polling만큼은 아니지만 웹 소켓도 서버에 부담을 준다.
    - 메세지들이 오가는 빈도가 높으면 네트워크 대역폭과 cpu 사용량 증가

## SSE (Server Send Events)

서버에서 클라이언트로만 데이터를 보낼 수 있는 **단방향**통신 기술이다. 라디오 방송처럼 서버는 계속 방송하고, 클라이언트는 듣기만 하는 구조이다.

서비스에 따라서 양방향 통신이 아닌 서버로 부터 단방향 통신으로도 충분한 경우가 있다.

- 서버에서 클라이언트에게 실시간으로 데이터를 보내면 됨 (sns, 실시간 모니터링 등)

sse는 웹 소켓에 비해 단순하다.

### **작동 원리**

1. **요청**: 클라이언트가 서버에 `Accept: text/event-stream` 헤더를 담아 요청을 보낸다.
2. **응답 & 유지**: 서버는 `Content-Type: text/event-stream`으로 응답하면서, 연결을 끊지 않고 계속 열어두는 `Connection: keep-alive` 설정 (한번의 연결로 지속적인 통신 가능)
3. **전송**: 서버는 이벤트가 발생할 때마다 데이터를 스트림 형태로 계속 내려보낸다.

이 과정이 하나의 연결 안에서 계속 이뤄짐, 만약 연결이 끊기면 클라이언트는 자동으로 재연결 요청

작업을 마치면 클라이언트/서버에서 상대에게 종료를 통보하는 메세지 보냄과 동시에 연결 끝

이 과정이 HTTP를 통해 이뤄지고 다른 설정 필요없다.

서버 쪽에서만 메세지를 보내기에 웹소켓과 달리 로드벨런싱이 되어있는 환경에서도 사용하기에 큰 어려움이 없다. 

클라이언트는 지정된 url로 서버에 요청을 보냄 → 해당 요청에는 sse 통신을 통해 이벤트 스트림이라는 형식의 메세지를 수신하겠다는 의미의 헤더가 실림

클라이언트는 복잡한 설정 없이 자바스크립트의 **`EventSource`** 라는 객체를 생성하면 된다.
서버 주소만 넣으면 연결 요청부터 재연결 처리까지 브라우저가 해준다.
